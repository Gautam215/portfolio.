# DATABASE.md — Abhishek Kumar Gautam Portfolio

Complete data model for this application. Source of truth: the PRD,
ARCHITECTURE.md, and the two schema files actually in the repo
(`db/migrations/001_contact_messages.sql` and
`001_contact_messages.postgres.sql`). This document describes the
model as built — it does not propose tables that do not exist.

## Database technology

- **Local / single server:** SQLite via Node 24's built-in
  `node:sqlite`. File: `data/portfolio.db` by default
  (`DATABASE_PATH`; relative paths scoped to `./data/`).
  Journal mode WAL, busy timeout 5s, foreign keys ON.
- **Production (Vercel):** Postgres via Neon (free tier, project
  `portfolio`, AWS Asia Pacific 1 Singapore, database `neondb`,
  production branch, pooling enabled). SQLite cannot reliably
  persist on Vercel (ephemeral, unshared serverless storage), so
  production must use Postgres.
- **Selection:** `lib/db.ts` — `DATABASE_URL` starting with
  `postgres://`/`postgresql://` → Postgres (`pg`, pool max 5);
  otherwise SQLite. One store interface (`ContactStore`) covers both,
  so routes never touch a driver directly.
- **No ORM.** One table does not justify one.

## Tables

There is exactly one table. This is intentional: the only data the
portfolio stores is contact messages. Projects, skills, education,
and certifications are resume content rendered from `lib/data.ts`,
not database rows, and inventing tables for them would be duplication.

### `contact_messages`

| Column | SQLite type | Postgres type | Null | Default | Notes |
|---|---|---|---|---|---|
| `id` | TEXT | TEXT | NOT NULL | — | Primary key. UUID generated by the route (`crypto.randomUUID()`). |
| `name` | TEXT | TEXT | NOT NULL | — | Sender name, trimmed. CHECK: length 2–100. |
| `email` | TEXT | TEXT | NOT NULL | — | Sender email, trimmed. Format validated in code (regex); no DB-level email format check. |
| `message` | TEXT | TEXT | NOT NULL | — | Message body, trimmed. CHECK: length 10–2000. |
| `ip_hash` | TEXT | TEXT | NOT NULL | — | SHA-256 hex of the sender IP. The raw IP is never stored. |
| `email_status` | TEXT | TEXT | NOT NULL | `'pending'` | CHECK: one of `pending`, `sent`, `failed`, `no_smtp`. |
| `email_error` | TEXT | TEXT | NULL | — | Short SMTP error text on `failed` (first 200 chars, server-side only); NULL otherwise. |
| `sent_at` | TEXT | TIMESTAMPTZ | NULL | — | Set to now() when status becomes `sent`; NULL otherwise. |
| `created_at` | TEXT | TIMESTAMPTZ | NOT NULL | SQLite: `strftime('%Y-%m-%dT%H:%M:%fZ','now')` / Postgres: `now()` | Insert time, never updated. |
| `updated_at` | TEXT | TIMESTAMPTZ | NOT NULL | Same as `created_at` | Updated on every status change. |

SQLite timestamps are ISO text; Postgres timestamps are
`TIMESTAMPTZ`. The migration script copies values across as-is
(they are the same ISO strings); the app maps both to ISO strings
in `ContactMessageRow`.

### Primary / foreign keys

- Primary key: `contact_messages.id` (TEXT, UUID).
- Foreign keys: none. There are no other tables, so there is nothing
  to reference. Do not add a foreign key without adding the table it
  references, and do not add a table without a PRD requirement.

## Constraints and validation

Constraints live in two layers, and both must agree:

| Rule | Database CHECK | Code validation (`lib/contact.ts` + route) |
|---|---|---|
| Name length | `char_length(name) BETWEEN 2 AND 100` (Postgres) / `length(name) BETWEEN 2 AND 100` (SQLite) | Trimmed length 2–100, else 400 |
| Message length | `char_length(message) BETWEEN 10 AND 2000` / `length(message) BETWEEN 10 AND 2000` | Trimmed length 10–2000, else 400 |
| Email format | — (no DB check) | Regex `^[^\s@]+@[^\s@]+\.[^\s@]+$`, else 400 |
| Status values | `email_status IN ('pending','sent','failed','no_smtp')` | Only those four values are ever written (insert `pending`; updates `sent`/`failed`/`no_smtp`) |
| Body size | — | Route rejects `Content-Length` > 32 KB with 413 |
| Rate | — | 5 POSTs/minute/IP, in-memory, per instance, else 429 |

The Postgres CHECK constraints were in the SQL executed in Neon,
but the dashboard verification output listed columns and indexes,
not constraints by name — so constraints are applied-by-SQL, not
independently listed (see IMPLEMENTATION_CHECKLIST.md). A future
read-only check against `information_schema` / `pg_constraint` can
close that verification gap without changing any data.

## Indexes, based on real queries

| Index | Columns | Justification (real query) |
|---|---|---|
| `contact_messages_pkey` (automatic) | `id` | `SELECT … WHERE id = ?` (get after insert; status updates by id) |
| `idx_contact_messages_created_at` | `created_at` | `SELECT … ORDER BY created_at ASC` (migration copy; chronological reading) |
| `idx_contact_messages_email_status` | `email_status` | Filtering by delivery state is the only status-based access pattern (owner review of `failed`/`no_smtp` rows) |

No other index is justified: there are no search, pagination, or
join queries in this app. Do not add indexes for hypothetical queries.

## Ownership and authorization

- **Neon:** the production database is accessed with the project's
  pooled connection string (role `neondb_owner`, the Neon default
  owner role). This is broader than least privilege, and it is
  documented here honestly rather than hidden: creating a separate,
  least-privilege app role is a possible hardening step, but it is
  not the current configuration, and no such role should be claimed
  to exist. The mitigation in place is architectural — the only
  process holding the string is the server, and no client or API
  endpoint can issue arbitrary queries.
- **SQLite:** the file is owned by the server process, gitignored
  (`*.db`), and never served over HTTP (verified: database file
  over HTTP returns 404).
- **Application-level authorization:** there is no per-user
  authorization because there are no users (see ARCHITECTURE.md
  §6). Writes are public but rate-limited and validated; reads of
  messages happen only by the owner, directly from the database.

## Row-level security

Not enabled, and not applicable as currently designed: RLS protects
multi-tenant data accessed by different database roles, and this app
has one owner, one table, and no direct database access from clients
at all. Enabling RLS with a single owner role would add complexity
without a security boundary it actually enforces. If a future admin
view or multi-user feature is approved, RLS (or its equivalent) must
be designed at that point, not retrofitted by assertion.

## Sensitive-data handling

- **Email addresses and message bodies are personal data.** They are
  stored only because the contact feature requires them, never
  returned by any endpoint, never logged, and never included in
  health output, error bodies, or build output.
- **IP addresses are never stored raw.** Only the SHA-256 hex hash
  (`ip_hash`) is stored, for abuse review and rate-limit context.
  Hashing is one-way; the original IP cannot be recovered from a row.
- **SMTP credentials and `DATABASE_URL` are secrets.** They live
  only in environment variables (Vercel dashboard in production,
  `.env.local` locally, gitignored). They never appear in code,
  docs, logs, or error messages. Migration scripts print counts
  only — never message contents, emails, or connection strings.
- **Email error text** stored in `email_error` is capped at 200
  characters and is server-side only; the client-facing failure
  message is a generic direct-email fallback, not the SMTP error.

## Migration and seed strategy

- **Schema migrations:** both schema files are idempotent
  (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`)
  and safe to re-run. The Postgres store also auto-applies its
  schema on first use, so a fresh deployment self-heals if the
  manual step was missed.
- **Scripts:**
  - `npm run db:migrate` — applies the Postgres schema to
    `DATABASE_URL`. (From this VM it is blocked by the runtime
    Databases permission — direct Neon TCP fails at TLS before
    auth. The working path used was the Neon dashboard SQL Editor,
    which applies the same SQL over the web console.)
  - `npm run db:migrate-sqlite` — copies every SQLite row to
    Postgres, preserving id, fields, status, error, and timestamps,
    `ON CONFLICT (id) DO NOTHING`, so re-runs are safe. At last
    check the SQLite file was empty (0 rows), so there was nothing
    to copy — but the script remains the preservation path.
- **Seed data:** none. No fake contact messages, no demo rows, no
  test rows in production. Test rows created during local
  verification are deleted afterwards; the local SQLite file is
  left empty. Seeding production with invented messages would
  violate the no-invention rule.
- **Schema changes:** a future column or table requires a new
  migration file (never an edit to `001_*` in place, which would
  break the idempotency guarantee for databases that already ran
  `001`), plus updates to both schema files, `db-types.ts`, both
  stores, and this document.

## Backup and recovery considerations

- **Neon (production):** backups are provider-managed. The owner
  must confirm the retention / point-in-time recovery terms of the
  free-tier project in the Neon dashboard before launch — this
  document does not claim a retention period that was not verified.
- **SQLite (local):** the file is a single file; recovery is a file
  copy. It holds no production data (production is Postgres), so
  local backup is not a launch requirement.
- **Recovery test:** none has been performed (no restore has been
  attempted on either database). A restore drill is a pre-launch
  verification item for the owner, not a claimed capability.
- **What is recoverable without a backup:** the schema itself
  (both files are in the repo and idempotent), and the page content
  (`lib/data.ts` in the repo). Only submitted contact messages
  would be lost if the production database were lost without a
  provider backup — which is why the backup confirmation above
  matters.
